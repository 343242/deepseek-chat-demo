## 表详情

### 1. sys_user — 用户表

| 列名 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | `BIGINT` | PK, GENERATED BY DEFAULT AS IDENTITY | 用户 ID（雪花算法生成） |
| `username` | `VARCHAR(50)` | NOT NULL | 用户名，软删除后可复用 |
| `password` | `VARCHAR(100)` | NOT NULL | BCrypt 哈希 |
| `nickname` | `VARCHAR(50)` | | 昵称 |
| `email` | `VARCHAR(100)` | | 邮箱 |
| `phone` | `VARCHAR(20)` | | 手机号 |
| `avatar` | `VARCHAR(255)` | | 头像 URL |
| `status` | `SMALLINT` | NOT NULL, DEFAULT 1 | 状态：1=启用 |
| `created_at` | `TIMESTAMPTZ` | NOT NULL, DEFAULT NOW() | 创建时间 |
| `updated_at` | `TIMESTAMPTZ` | | 更新时间 |
| `deleted` | `SMALLINT` | NOT NULL, DEFAULT 0 | 逻辑删除：0=正常 |

**索引：**
| 名称 | 类型 | 列 | 条件 |
|------|------|-----|------|
| `sys_user_pkey` | UNIQUE | id | |
| `uk_user_username` | UNIQUE | username | WHERE deleted = 0 |
| `uk_user_email` | UNIQUE | email | WHERE deleted = 0 AND email IS NOT NULL |
| `idx_user_status` | btree | status | WHERE deleted = 0 |

**设计要点：**
- 使用 partial unique index 解决软删除下的唯一约束问题
- 邮箱允许 NULL，但非 NULL 时在未删除范围内唯一
- 密码使用 BCrypt（cost=10）哈希存储

### 11. team — 团队表（V9 新增）

| 列名 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | `BIGINT` | PK, GENERATED BY DEFAULT AS IDENTITY | 团队 ID |
| `team_name` | `VARCHAR(128)` | NOT NULL | 团队名称 |
| `team_desc` | `VARCHAR(512)` | | 团队描述 |
| `creator_id` | `BIGINT` | NOT NULL, FK → sys_user(id) | 创建者 |
| `default_upload_limit_mb` | `BIGINT` | NOT NULL, DEFAULT 50 | 成员默认上传限额(MB) |
| `creator_upload_limit_mb` | `BIGINT` | NOT NULL, DEFAULT 200 | 创建者上传限额(MB) |
| `status` | `SMALLINT` | NOT NULL, DEFAULT 1 | 状态：0=INACTIVE, 1=ACTIVE |
| `created_at` | `TIMESTAMPTZ` | NOT NULL, DEFAULT NOW() | 创建时间 |
| `updated_at` | `TIMESTAMPTZ` | NOT NULL, DEFAULT NOW() | 更新时间 |
| `deleted` | `SMALLINT` | NOT NULL, DEFAULT 0 | 逻辑删除 |

**索引：**
| 名称 | 类型 | 列 | 条件 |
|------|------|-----|------|
| `team_pkey` | UNIQUE | id | |
| `uk_team_name_active` | UNIQUE | team_name | WHERE deleted = 0 |
| `idx_team_creator` | btree | creator_id | |

**设计要点：**
- `team_name` 使用 partial unique index，软删除后可复用名称
- 创建者与成员分设上传限额，创建者默认更高
- 状态用 SMALLINT 枚举值（非 @TableLogic），0 表示停用

---

### 12. team_member — 团队成员表（V9 新增）

| 列名 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | `BIGINT` | PK, GENERATED BY DEFAULT AS IDENTITY | 成员记录 ID |
| `team_id` | `BIGINT` | NOT NULL, FK → team(id) | 团队 ID |
| `user_id` | `BIGINT` | NOT NULL, FK → sys_user(id) | 用户 ID |
| `role` | `SMALLINT` | NOT NULL, DEFAULT 10 | 角色：10=MEMBER, 20=ADMIN, 30=CREATOR |
| `upload_limit_mb` | `BIGINT` | NOT NULL, DEFAULT 50 | 个人上传限额(MB) |
| `status` | `SMALLINT` | NOT NULL, DEFAULT 1 | 状态：0=INACTIVE, 1=ACTIVE |
| `joined_at` | `TIMESTAMPTZ` | NOT NULL, DEFAULT NOW() | 加入时间 |
| `updated_at` | `TIMESTAMPTZ` | NOT NULL, DEFAULT NOW() | 更新时间 |

**索引：**
| 名称 | 类型 | 列 | 条件 |
|------|------|-----|------|
| `team_member_pkey` | UNIQUE | id | |
| `uk_team_user_active` | UNIQUE | team_id, user_id | WHERE status = 1 |
| `idx_team_member_user` | btree | user_id, status | |

**设计要点：**
- 用 partial unique index 保证同一用户在活跃团队中唯一
- 角色分三级：MEMBER（10）、ADMIN（20）、CREATOR（30）
- `status` 不使用 @TableLogic，0=INACTIVE 时允许同一用户重新加入同一团队
- 每人可有独立的 `upload_limit_mb`，覆盖团队默认值

### 13. team_upload_approval — 团队上传审批表（V9 新增）

| 列名 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | `BIGINT` | PK, GENERATED BY DEFAULT AS IDENTITY | 审批 ID |
| `team_id` | `BIGINT` | NOT NULL, FK → team(id) | 团队 ID |
| `document_id` | `BIGINT` | NOT NULL, FK → rag_document(id) | 文档 ID |
| `uploader_id` | `BIGINT` | NOT NULL, FK → sys_user(id) | 上传者 |
| `status` | `SMALLINT` | NOT NULL, DEFAULT 0 | 状态：0=PENDING, 1=APPROVED, 2=REJECTED |
| `reviewer_id` | `BIGINT` | FK → sys_user(id) | 审批人（审批后填充） |
| `review_comment` | `VARCHAR(512)` | | 审批意见 |
| `created_at` | `TIMESTAMPTZ` | NOT NULL, DEFAULT NOW() | 提交时间 |
| `reviewed_at` | `TIMESTAMPTZ` | | 审批时间 |

**索引：**
| 名称 | 类型 | 列 | 条件 |
|------|------|-----|------|
| `team_upload_approval_pkey` | UNIQUE | id | |
| `idx_approval_team_status` | btree | team_id, status | |
| `idx_approval_uploader` | btree | uploader_id | |

**设计要点：**
- 审批流程：PENDING → APPROVED / REJECTED
- `reviewer_id` 和 `reviewed_at` 在审批操作时填充
- 联合索引 `idx_approval_team_status` 用于按团队 + 状态快速查询待审批列表

## Redis 使用

数据库外的补充存储，不属于 PostgreSQL 表：

| Key 模式 | TTL | 用途 |
|----------|-----|------|
| `auth:token:access:{userId}:{jti}` | 900s | Access Token 元数据 + 角色列表 |
| `auth:token:refresh:{tokenHash}` | 86400s | Refresh Token → userId 映射 |
| `auth:status:{userId}` | — | 用户状态标记 (disabled/deleted) |
| `auth:perm:{userId}` | 300s | 用户权限缓存 |
| `auth:login:{ip}` | 300s | IP 登录尝试计数 |

## 潜在问题与改进建议

| # | 问题 | 建议 |
|---|------|------|
| 1 | `spring_ai_chat_memory.created_at` 用 `TIMESTAMP` 无时区，与其他表的 `TIMESTAMPTZ` 不一致 | Spring AI 管控的表，暂不动；长期可考虑自定义 Schema |
| 2 | `token_usage` 无 `user_id` 列，无法按用户统计 | 新增 `user_id BIGINT` 列并加索引 |
| 3 | `sys_permission.parent_id` 预留了树形但未使用 | 如不需要层级权限可移除，简化模型 |
| 4 | `model_params` 用 KV 模式查询时需要聚合 | 如果参数固定（temperature/topP/maxTokens 等），可改为列式存储 |
| 5 | 软删除的关联表（sys_user_role, sys_role_permission）没有清理逻辑 | 删除用户/角色时应清理关联数据 |
| 6 | `team_member.status` 使用 SMALLINT 枚举（非 `deleted` 字段），与 `team.deleted` 的软删除模式不一致 | 有意设计：成员离开团队（INACTIVE）是业务操作，不同于数据逻辑删除；且 partial unique index `WHERE status=1` 允许成员离开后重新加入 |
| 7 | `rag_document.team_id` 允许 NULL 以兼容 V9 前历史数据 | 长期可考虑 NOT NULL 并补全历史数据，简化查询和索引逻辑 |
| 8 | `team_upload_approval.reviewer_id` 为 NULLABLE 外键，审批前为空 | 符合业务逻辑——审批完成前审批人未知；如需约束可加 CHECK 确保 APPROVED/REJECTED 时 reviewer_id 非空 |
