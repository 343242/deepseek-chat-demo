## 2. 登录页 vs 注册页字段对比

注册页与登录页**共用同一 AuthShell 和卡片框架**，仅字段不同。切换通过底部链接，无路由刷新感（卡片内容渐变切换）。

### 2.1 登录页字段

| 字段 | label | placeholder | 校验（后端） | 错误文案 |
|------|-------|-------------|-------------|---------|
| 用户名 | 用户名 | 请输入用户名 | `@NotBlank`（LoginRequest:6） | 用户名不能为空 |
| 密码 | 密码 | 请输入密码 | `@NotBlank`（LoginRequest:7） | 密码不能为空 |
| 滑块验证码 | — | 向右拖动完成验证 | captchaId + captchaCode（滑块 x 坐标，随表单一起提交；LoginRequest:8-9） | 验证失败，请重试 |

> 提交 `POST /api/auth/login` 时请求体含 4 个字段：`{ username, password, captchaId, captchaCode }`。captchaId 来自 `GET /api/auth/captcha`，captchaCode 是滑块松手时的 x 像素位移。

### 2.2 注册页字段

| 字段 | label | placeholder | 校验（后端） | 错误文案 |
|------|-------|-------------|-------------|---------|
| 用户名 | 用户名 | 2-50 字符 | `@NotBlank` + `@Size(min=2,max=50)`（RegisterRequest:8） | 用户名长度必须为2到50个字符 |
| 密码 | 密码 | 8-72 字符 | `@NotBlank` + `@Size(min=8,max=72)`（RegisterRequest:9） | 密码长度必须为8到72个字符 |
| 邮箱 | 邮箱 | name@example.com | `@NotBlank` + `@Email` + `@Size(max=100)`（RegisterRequest:10） | 邮箱格式不正确 |
| 昵称（可选） | 昵称 | 选填，最多 50 字符 | `@Size(max=50)`（RegisterRequest:11） | 昵称最多50个字符 |
| 确认密码 | 确认密码 | 再次输入密码 | 前端：与密码一致 | 两次密码不一致 |
| 滑块验证码 | — | 向右拖动完成验证 | 同登录（captchaId + captchaCode，RegisterRequest:12-13） | 验证失败，请重试 |

> 提交 `POST /api/auth/register` 时请求体含 6 个字段：`{ username, password, email, nickname, captchaId, captchaCode }`（nickname 可空）。错误文案原样使用后端 message。

> 注册页布局与登录页相同，只是字段纵向增多，卡片高度自适应。底部链接变为"已有账号？[登录]"。

## 3. 滑块验证码组件详图（SliderCaptcha）

这是认证页的核心差异化组件（DS 11.1）。基于 `CaptchaResult { captchaId, backgroundImage(310×155), puzzleImage(≈79×79) }`。

### 3.1 默认态结构

> **拼图块 y 固定居中**：后端生成的缺口与抠出的 puzzleImage 都在背景图的垂直居中行（`answerY = (155-47)/2 = 54`）。前端把 puzzleImage 的 `top` 写死为 `39px`（= `answerY - padding`，padding≈15），用户**只需水平拖动**，无需垂直对齐。x 方向缺口位置随机（安全边界，bot 必须图像识别才能定位）。

```
┌─ 滑块验证码 ─────────────────────────────────┐
│  ↻刷新                                       │  ← 右上角刷新按钮（小图标）
│                                             │
│  ┌─────────────────────────────────────┐    │
│  │                                     │    │  ← backgroundImage
│  │   ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓                  │    │     310×155 PNG
│  │   ▓▓▓▓ [缺口] ▓▓▓▓                  │    │     缺口 y 固定居中，x 随机
│  │   ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓                  │    │
│  │                                     │    │
│  │   ┌──┐                              │    │  ← puzzleImage（top 固定 39px）
│  │   │ Puzzle │  ← 跟随滑块 x 位移       │    │     仅水平拖动，y 不变
│  │   └──┘                              │    │     初始在左侧（left:0）
│  └─────────────────────────────────────┘    │
│                                             │
│  ┌─────────────────────────────────────┐    │
│  │ ▶  ━━━━━━━━━━━━━━━━━━━━━━━━━━ ●    │    │  ← 滑块轨道
│  │    向右拖动完成验证                   │    │     高 40px
│  └─────────────────────────────────────┘    │
└─────────────────────────────────────────────┘
```

### 3.2 六态详图

| 状态 | 视觉 | 触发 | 色值 |
|------|------|------|------|
| **待验证** | 滑块在左，拼图在左，轨道 `--neutral-100`，文案"向右拖动完成验证" | 初始 / 刷新后 | 中性 |
| **拖拽中** | 拼图跟随滑块 x 位移，轨道已过部分填充 `--brand-50` | 按住拖动 | brand 浅 |
| **验证中** | 滑块禁用，Loader 旋转，文案"验证中…" | 松手提交 | brand |
| **成功** | 滑块到右，轨道变 `--success-600`，`CheckCircle2` + "验证成功" | 后端确认 | success |
| **失败** | 拼图抖动回弹左侧，轨道闪 `--error-600` 0.5s，文案"验证失败，请重试" | 校验失败（容差 ±5px 外） | error |
| **过期** | 文案"验证码已过期"，`RefreshCw` 刷新按钮高亮 | captchaId 超 5 分钟（CaptchaService.java:77） | warning |

### 3.3 交互规则

- **拼图块垂直固定**：puzzleImage 的 `top` 写死 `39px`（= `answerY(54) - padding(15)`），用户只水平拖动。y 不随机（后端固定居中），前端无需任何垂直对齐逻辑
- **captchaCode = 拼图块左边缘 x 坐标**：注意 puzzleImage 内拼图块在 `padding(15)` 处，所以 `captchaCode = puzzleImage.left + 15`（不是裸 puzzleImage.left）。即用户拖动位移需补偿 padding 后上报
- **容差 ±5px**（`CaptchaService.java` TOLERANCE=5），用户无需精确对齐
- **失败后自动刷新**：获取新 captcha（避免 captchaId 复用），拼图归位
- **手动刷新**：右上角 ↻ 按钮，立即换图
- **TTL 5 分钟**：过期需重新获取
- **dev 环境**：后端返回 `answer`（正确 x 坐标）便于自动化测试；生产为 null

## 4. 状态详图（5 态 + 锁定态）

### 4.1 默认态

如 §1 所示，所有输入框空，滑块待验证，按钮禁用（disabled 样式）。

> **按钮启用条件**：用户名 + 密码 + 验证成功 三者齐全才可点。未齐全时按钮 `--neutral-100` 底、`--text-disabled` 文字。

### 4.2 输入中（带即时校验）

```
┌──────────────────────────────────┐
│ 👤 admin                          │  ← 输入有效，无错误
├──────────────────────────────────┤
│ 🔒 ••••••••           [👁隐藏]    │  ← 密码默认掩码
└──────────────────────────────────┘
```

- 失焦时校验（前端 zod 规则与后端注解对齐）
- 错误时输入框边框 `--border-error`，下方红字提示

### 4.3 校验错误态

```
┌──────────────────────────────────┐  ← 边框 --border-error
│ 👤 a                              │
└──────────────────────────────────┘
⚠ 用户名需 2-50 字符                  ← 红字 --error-600, --font-size-sm
```

### 4.4 提交中（loading）

```
┌──────────────────────────────────┐
│           ◌ 验证中…               │  ← Loader 旋转替换文字，按钮禁用
└──────────────────────────────────┘
```

### 4.5 登录失败（凭据错误）

```
┌─ 登录卡顶部错误条 ──────────────────────────┐
│ ⚠️ 用户名或密码错误                          │  ← --error-50 底
└─────────────────────────────────────────────┘     --error-600 文字
```

- 错误条出现在卡片顶部（Logo 下方），自动消失或手动关闭
- 密码框清空，焦点回到密码框
- 滑块验证码**刷新**（单次使用，已消费）

### 4.6 IP 限流态（⚠️ 关键）

后端：**per-IP 滑动窗口限流**（`RateLimitProperties` + `AuthServiceImpl`，Redis Lua 原子递增），无"账户锁定"概念：
- 登录：默认 **30 次 / 30 分钟**（`ratelimit:login:*` key）
- 注册：默认 **10 次 / 20 分钟**（`ratelimit:register:*` key，独立计数，互不消耗）
- ⚠️ **错误验证码不消耗登录 IP 配额**——验证码先于限流校验（避免被用来恶意锁死账户）；只有通过验证码后的登录/注册尝试才计数
- 阈值可在 `app.ratelimit.*` 覆盖（生产可调紧）

```
┌─ 登录卡顶部错误条 ──────────────────────────┐
│ 🔒 登录尝试过于频繁，请稍后再试              │  ← --error-50 底
└─────────────────────────────────────────────┘     --error-600 文字（后端 message）
```

- 后端返回 `RateLimitExceededException`（消息"登录尝试过于频繁，请稍后再试"），前端原样显示后端 message
- 前端不显示"还剩 N 次"——后端不暴露剩余次数；TTL 由 Redis key 过期决定（首次失败起 30 分钟窗口滑动），前端无法精确告知

### 4.7 登录成功

无特殊视觉——直接跳转着陆页（见 §5）。

## 5. 登录后跳转流（IA 4.2）

```
登录成功（200 + Set-Cookie）
  │
  ├─ 缓存 LoginResponse.user（含 roles）
  │
  ├─ roles 含 ADMIN?
  │   ├─ 是 → 跳 /admin（重定向到首个有权限的子页）
  │   └─ 否 → 跳 /app/chat
  │
  └─ 检查 URL ?redirect= 参数
      ├─ 有且为本站路径 → 跳 redirect（防开放重定向）
      └─ 无 → 用上述角色判定
```

> Token 在 HttpOnly Cookie 里（前端 JS 不可读），无需手动存储。前端只需缓存 `user` 对象供权限守卫用。
