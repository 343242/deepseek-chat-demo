## 一、数据库设计

### P0-1：`team_member` 软删除机制与项目规范冲突

**问题描述：** PRD 定义 `team_member` 使用 `status INT` 字段实现软删除（1=正常 0=已移除），而项目规范明确定义软删除应使用 `deleted SMALLINT NOT NULL DEFAULT 0` 配合 `@TableLogic`。这种不一致会导致：

1. MyBatis-Plus 的 `@TableLogic` 自动过滤无法生效，所有查询必须手动加 `status = 1`
2. 团队其他成员通过 `LambdaQueryWrapper` 查询时会忘记过滤已移除的成员
3. 代码审查时容易误以为 `team_member` 没有软删除逻辑

**违反规范：**
- `database-guidelines.md`：软删除 → `deleted SMALLINT NOT NULL DEFAULT 0`，用 `@TableLogic`
- `quality-guidelines.md` Security Checklist：软删除 → 查询条件必须包含 `deleted = 0`
- 设计原则：不走捷径

**建议修复：**

```sql
-- team_member 改为标准软删除模式
CREATE TABLE team_member (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    team_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    role VARCHAR(32) NOT NULL DEFAULT 'MEMBER',
    upload_limit_mb BIGINT,
    deleted SMALLINT NOT NULL DEFAULT 0,  -- 标准软删除
    joined_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT uk_team_user UNIQUE (team_id, user_id)  -- 配合 partial index
);
-- partial unique index 兜底
CREATE UNIQUE INDEX uk_team_user_active ON team_member(team_id, user_id) WHERE deleted = 0;
```

### P0-2：`team.team_name` 唯一约束缺少软删除兜底

**问题描述：** PRD 定义 `team_name VARCHAR(128) NOT NULL, UNIQUE`。但 `team` 表有 `deleted` 字段支持软删除（解散团队）。解散后团队名应该可以被新团队使用。当前的全字段 UNIQUE 约束会阻止这一场景。

**违反规范：**
- `database-guidelines.md`：唯一约束 → "使用 partial unique index: `WHERE deleted = 0`"
- `quality-guidelines.md`：Security Checklist → "业务层先查重 + 数据库 partial unique index 兜底"

**建议修复：**

```sql
-- 替换全字段 UNIQUE 为 partial unique index
team_name VARCHAR(128) NOT NULL,
-- 移除 UNIQUE 关键字

CREATE UNIQUE INDEX uk_team_name_active ON team(team_name) WHERE deleted = 0;
```

业务层先 `SELECT` 检查 `deleted = 0` 的同名团队是否存在。

---

### P0-3：`team` 状态字段与 `deleted` 字段功能重叠

**问题描述：** PRD 在 `team` 表同时定义了 `status INT NOT NULL DEFAULT 1`（1=启用 0=禁用）和 `deleted INT NOT NULL DEFAULT 0`。`status = 0`（禁用）和 `deleted = 1`（逻辑删除）在语义上高度重叠。当前没有"禁用但不删除"的业务场景（4.1.3 解散团队是直接逻辑删除）。

**违反规范：**
- `database-guidelines.md`：列定义约定 → 最小必要原则
- 设计原则：SOLID 单一职责

**建议修复：** 去掉 `status` 字段或明确定义其与 `deleted` 的区别。如果本期没有"禁用"场景，先去除此字段。如果有未来扩展需要（如"封禁团队"），则应在 PRD 中补充该场景。

---

### P1-1：`deleted` 列类型应为 `SMALLINT` 而非 `INT`

**问题描述：** PRD 中 `team.deleted` 和 `team_member.deleted`（如果采纳 P0-1）定义为 `INT`，但项目规范明确要求 `SMALLINT`。`INT` 浪费存储且与项目中所有其他表的 `SMALLINT` 不一致。

**违反规范：**
- `database-guidelines.md`：列定义约定 → "软删除 `deleted SMALLINT NOT NULL DEFAULT 0`"

**建议修复：** `deleted SMALLINT NOT NULL DEFAULT 0`

---

### P1-2：`team_member.role` 应使用枚举而非裸 `VARCHAR`

**问题描述：** PRD 定义 `role VARCHAR(32) NOT NULL DEFAULT 'MEMBER'`，可选值 CREATOR / ADMIN / MEMBER。但项目设计原则明确要求"实体用枚举不用 String"。PRD 在模块结构中列出了 `TeamMemberRole.java` 枚举，但数据库定义没有配合 `@EnumValue` 映射模式。

**违反规范：**
- `quality-guidelines.md`：Security Checklist → "状态枚举：用枚举类约束，不接受裸 Integer"
- `quality-guidelines.md`：Forbidden Patterns → "裸 Integer 状态字段 → 枚举类 + 校验"
- 设计原则：实体用枚举不用 String

**建议修复：** 在 `TeamMember.java` 实体中使用 `@EnumValue` 注解 `role` 字段，配合 `TeamMemberRole` 枚举（参考现有 `EtlStatus`、`ConversationStatus` 的模式）。数据库层 `VARCHAR` 可以保留，但 Java 侧必须用枚举。

---

### P1-3：`team.updated_at` 与现有命名不一致

**问题描述：** PRD 新表使用 `created_at` / `updated_at`（snake_case 风格），但现有表命名存在三种不同风格：

| 表 | 时间列 |
|----|--------|
| `sys_user` | `created_at` / `updated_at` |
| `rag_document` | `create_time` / `update_time` |
| `team` | `created_at` / `updated_at` |

**违反规范：**
- `database-guidelines.md`：命名约定 → 保持一致性

**建议修复：** 统一为 `created_at` / `updated_at`，现有表可在后续迁移中重命名。新增表统一用 `created_at` / `updated_at` 搭配 `TIMESTAMPTZ`。

---

### P2-1：`BIGINT` 作为上传额度字段类型过大

**问题描述：** `default_upload_limit_mb` 和 `creator_upload_limit_mb` 使用 `BIGINT`，但 MB 级别的上传额度最大值不可能超过 INTEGER 范围（2,147,483,647 MB ≈ 2PB）。使用 `INTEGER` 即可。

**建议修复：** `default_upload_limit_mb INTEGER DEFAULT 50`

---

### P2-2：`team_upload_approval` 缺少创建/更新时间追踪字段

**问题描述：** 审批表有 `created_at` 但没有 `updated_at`。当审批被处理（通过/拒绝），`reviewed_at` 记录了处理时间，但通用 `updated_at` 也是项目惯例，缺少会导致审计不一致。

**建议修复：** 添加 `updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`。

---

### P2-3：缺少 FK 命名约定

**问题描述：** PRD 使用匿名的 FK 约束（`FK → sys_user(id)`），但没有明确的 FK 命名规范。PostgreSQL 会自动生成名称，不利于后期 DBA 维护。

**建议修复：** 明确定义 FK 名称，如 `fk_team_creator FOREIGN KEY (creator_id) REFERENCES sys_user(id)`。

## 二、API 设计

### P1-4：`DELETE /api/teams/{teamId}/members/{userId}` 语义过载

**问题描述：** 同一个 DELETE 端点承担两个不同操作：
1. CREATOR 移除其他成员
2. 用户本人退出团队

RESTful 语义上，DELETE 资源应表示"移除该资源"，但"退出团队"是操作者对自己执行的动作，语义不同。且两者的权限校验逻辑完全不一样（CREATOR 能移除任何人 vs. 本人只能移除自己）。

**违反规范：**
- 设计原则：接口命名要准确

**建议修复：** 分离为两个端点：
- `DELETE /api/teams/{teamId}/members/{userId}` — 仅 CREATOR 移除成员
- `POST /api/teams/{teamId}/members/leave` — 本人退出团队（或 `DELETE /api/teams/{teamId}/members/me`）

---

### P1-5：文档接口 `GET /api/documents` 混合个人和团队文档

**问题描述：** PRD 6.4 节说 `GET /api/documents` 返回"个人文档 + 团队文档（标注 teamId）"。这会改变现有端点行为，且混在一起需要调用方额外过滤。更好的设计是保留原端点不变，团队文档通过新增的 `GET /api/teams/{teamId}/documents` 单独获取。

**违反规范：**
- `cross-layer-thinking-guide.md`：API ↔ Service → "Type mismatches, missing fields"
- 设计原则：SOLID 单一职责

**建议修复：** `GET /api/documents` 保持不变（仅个人文档）。团队文档通过 `GET /api/teams/{teamId}/documents` 获取（PRD 已定义此端点，但应在 4.5.1 中明确说明）。

### P2-4：审批列表分页参数未定义

**问题描述：** PRD 4.4.1 说审批列表"（分页）"，但未定义分页参数（page, size, sort）。项目中已有 `PageRequest` 通用分页对象。

**建议修复：** 明确使用 `PageRequest` 作为分页入参，`PagedResult<ApprovalVO>` 作为出参。

### P2-5：成员列表缺少分页支持

**问题描述：** 4.2.5 查看成员列表没有分页能力。当团队有大量成员时（如 500+），返回全量成员列表会导致性能问题。

**建议修复：** 成员列表支持分页，使用 `PageRequest` / `PagedResult`。

### P2-6：缺少 Request/Response JSON Schema

**问题描述：** API 设计列出了端点和权限要求，但未提供任何请求/响应体 JSON 示例。实现阶段会引入歧义。

**建议修复：** 为每个端点补充 JSON 示例，至少包括 POST/PATCH 的 Request Body 和所有 GET 的 Response Body。

## 三、架构设计

### P0-4：上传逻辑分叉违反 OCP

**问题描述：** PRD 7.2 节明确说明在 `DocumentApplicationServiceImpl.upload()` 方法内"增加判断分支"区分个人上传和团队上传。这违反了项目强制执行的"开闭原则：加功能 = 加新类，不是改旧类"。

```
// 当前 PRD 设计（违反 OCP）：
public DocumentVO upload(MultipartFile file, Long teamId) {
    if (teamId != null) {
        // 团队上传流程：额度校验 + 审批
    } else {
        // 个人上传流程：直接上传 + ETL
    }
}
```

**违反规范：**
- `quality-guidelines.md`：Design Principles → "OCP 强制：新功能 = 新增类，不是改旧类"
- 设计原则：开闭原则（OCP），设计模式优先

**建议修复：** 使用策略模式，不在 `DocumentApplicationServiceImpl` 中加 if-branch：

```java
// 策略接口
public interface DocumentUploadStrategy {
    boolean supports(Long teamId);
    DocumentVO upload(MultipartFile file, Long teamId, Long userId);
}

// 个人上传策略（现有逻辑保持不变）
@Component
public class PersonalUploadStrategy implements DocumentUploadStrategy {
    public boolean supports(Long teamId) { return teamId == null; }
    // 原有逻辑一字不改
}

// 团队上传策略（新类）
@Component
public class TeamDocumentUploadStrategy implements DocumentUploadStrategy {
    public boolean supports(Long teamId) { return teamId != null; }
    // 团队流程：额度校验 + 审批
}

// DocumentApplicationServiceImpl 使用策略工厂
@Component
public class DocumentApplicationServiceImpl {
    private final List<DocumentUploadStrategy> strategies;
    
    public DocumentVO upload(MultipartFile file, Long teamId) {
        var strategy = strategies.stream()
            .filter(s -> s.supports(teamId))
            .findFirst().orElseThrow();
        return strategy.upload(file, teamId, currentUserId);
    }
}
```

这样可以做到零修改 `PersonalUploadStrategy`（原有逻辑），同时新增 `TeamDocumentUploadStrategy` 新类。

### P1-6：团队模块对 RAG 模块的直接依赖缺少抽象

**问题描述：** PRD 8 节中 `TeamApprovalService` 审批通过后触发 ETL，依赖 `EtlDispatchService`；`TeamService` 解散团队时依赖 `DocumentLifecycleService` 和 `MinioFileStorageService`。这些是跨模块的直接依赖，如果 RAG 模块内部变化，团队模块也要修改。

**违反规范：**
- `cross-layer-thinking-guide.md`：Leaky Abstractions → "每个层只应知道相邻层"
- 设计原则：封装彻底，厂商差异不泄漏到上层

**建议修复：** 在 RAG 模块暴露一个 Facade 接口（如 `RagCoordinator`），团队模块只依赖这个接口：

```java
// rag/service/RagCoordinator.java
public interface RagCoordinator {
    void triggerEtl(Long documentId);
    void cascadeDeleteTeamDocuments(Long teamId);
    void cascadeDeleteTeamVectors(Long teamId);
}
```

## 四、安全设计

### P0-5：`team_member` 非 `@TableLogic` 查询可能遗漏软删除过滤

**问题描述：** 如果 `team_member` 使用 `status` 而非 `deleted + @TableLogic`（P0-1），则任何通过 MyBatis-Plus `LambdaQueryWrapper` 的查询都不会自动过滤已移除的成员。例如：4.2.5 查看成员列表时如果不手动加 `.eq(TeamMember::getStatus, 1)`，已移除成员也会被列出。这是一个数据泄露风险。

**违反规范：**
- `quality-guidelines.md`：Security Checklist → "软删除：查询条件必须包含 `deleted = 0`"
- 设计原则：不走捷径

**建议修复：** 与 P0-1 合并修复：改用 `deleted SMALLINT + @TableLogic`。

---

### P1-8：团队创建者上传额度缺少数据库约束

**问题描述：** PRD 4.3.4 说系统管理员通过 API 设定 `creator_upload_limit_mb`，Service 层会校验，但数据库没有 CHECK 约束。如果直接操作数据库或 Service 层有 bug，可能写入负数或零值。

**违反规范：**
- `quality-guidelines.md`：Security Checklist → "状态枚举：用枚举类约束，不接受裸 Integer"
- `cross-layer-thinking-guide.md`：Define Contracts → "What errors can occur?"

**建议修复：** 添加 CHECK 约束：

```sql
creator_upload_limit_mb BIGINT NOT NULL DEFAULT 200 
    CHECK (creator_upload_limit_mb >= 1),
default_upload_limit_mb BIGINT NOT NULL DEFAULT 50 
    CHECK (default_upload_limit_mb >= 1)
```

---

### P1-9：缺少团队操作的频率限制

**问题描述：** PRD 没有提到对团队创建、加入团队等操作进行频率限制。恶意用户可以：
- 脚本批量创建数万个团队（数据库压力）
- 频繁加入/退出团队（日志膨胀）
- 短时间内提交大量审批请求

**违反规范：**
- `quality-guidelines.md`：Security Checklist → 缺少输入/频率校验

**建议修复：** 至少对"创建团队"和"加入团队"增加基于 IP 或 userId 的频率限制，复用现有的限流基础设施（`RateLimiter` 接口 + Redis）。

---

### P2-9：`team_member.role` 校验只依赖字符串比较

**问题描述：** PRD 9 节校验方法是 `member.getRole() != CREATOR`，这是字符串/枚举相等性比较。但如果 `role` 字段被非法修改为未知值，代码行为未定义。应该先验证 `role` 是否为合法枚举值。

**建议修复：** 在 `verifyTeamMember` 返回 `TeamMember` 后，使用 `TeamMemberRole` 枚举对 `role` 进行合法性校验。

## 五、跨层数据流

### P0-6：`RagDocument.status` 的 `EtlStatus` 枚举不包含 `PENDING_APPROVAL` 和 `REJECTED`

**问题描述：** 这是影响最大的跨层问题。PRD 4.3.1 和 4.4.2 定义了新的文档状态：

- 普通成员上传 → `rag_document.status = PENDING_APPROVAL`
- 审批通过 → `rag_document.status = UPLOADED`
- 审批拒绝 → `rag_document.status = REJECTED`

但现有 `EtlStatus` 枚举定义如下：

```java
public enum EtlStatus {
    UPLOADED, PARSING, CHUNKING, VECTORIZING, COMPLETED,
    FAILED, VECTOR_FAILED, PROCESSING
}
```

**不存在 `PENDING_APPROVAL` 和 `REJECTED`！**

如果不修改 `EtlStatus` 枚举（或创建新的字段/枚举），上传时写入 `PENDING_APPROVAL` 会导致数据库写入失败或类型转换异常。

**违反规范：**
- `cross-layer-thinking-guide.md`：Mistake 1 → "Implicit format assumptions"
- `cross-layer-thinking-guide.md`：Checklist → "Mapped the complete data flow"
- `quality-guidelines.md`：Security Checklist → "状态枚举：用枚举类约束"

**建议修复（两个方案选一）：**

**方案 A（推荐）：扩展 `EtlStatus` 枚举**

```java
public enum EtlStatus {
    PENDING_APPROVAL("PENDING_APPROVAL"),  // 新增：等待审批
    UPLOADED("UPLOADED"),
    PARSING("PARSING"),
    CHUNKING("CHUNKING"),
    VECTORIZING("VECTORIZING"),
    COMPLETED("COMPLETED"),
    FAILED("FAILED"),
    VECTOR_FAILED("VECTOR_FAILED"),
    REJECTED("REJECTED");  // 新增：审批拒绝
    // 保留 PROCESSING 或合并到 UPLOADED
}
```

**方案 B：新增独立字段 `rag_document.approval_status`**

分离 ETL 状态和审批状态，但会增加字段和查询复杂度。不建议。

注意：需要定义状态转换规则（State Machine），特别是 `PENDING_APPROVAL` → `UPLOADED` → PARSING → … 和 `PENDING_APPROVAL` → `REJECTED`。`REJECTED` 是终态。还缺 `PENDING_APPROVAL` 是否可以回退到 UPLOADED 以外的状态。

### P1-10：Entity 时间类型不一致

**问题描述：** 现有 `RagDocument` 使用 `LocalDateTime`（对应 `TIMESTAMP`），而 PRD 新表使用 `TIMESTAMPTZ`（对应 `OffsetDateTime`）。当 `team_upload_approval` 关联 `rag_document(id)` 时，一个带时区一个不带，在比较和计算时可能导致时区偏差。

具体问题：
- `sys_user` 使用 `OffsetDateTime` ✅
- `rag_document` 使用 `LocalDateTime` ❌
- `team` 使用 `TIMESTAMPTZ` → 应该映射到 `OffsetDateTime`
- `team_upload_approval` 使用 `TIMESTAMPTZ` → 同上

**违反规范：**
- `database-guidelines.md`：列定义约定 → "时间列：`TIMESTAMPTZ`（带时区），不用 `TIMESTAMP`"
- `cross-layer-thinking-guide.md`：Checklist → "Data survives round-trip"

**建议修复：** 所有新 entity 统一使用 `OffsetDateTime`。`RagDocument` 的 `LocalDateTime` 在后续迁移中改为 `OffsetDateTime`（本次 PRD 可先不处理，但应在风险评估中记录）。

### P1-11：审批超时自动拒绝的事务边界模糊

**问题描述：** PRD 4.4.3 说超时后"自动拒绝 + 删除 MinIO 文件"。这个操作跨越：
1. 更新 `team_upload_approval`（DB）
2. 更新 `rag_document.status`（DB）
3. 删除 MinIO 文件（外部存储）

删除 MinIO 文件是外部 I/O，不应在 DB 事务内执行。如果删除 MinIO 文件失败，前面的 DB 更新是否回滚？PRD 未定义事务边界。

**违反规范：**
- `database-guidelines.md`：事务 → "统一使用 `TransactionTemplate` 编程式事务"
- 设计原则：多表写入必须用事务

**建议修复：**

```java
// 伪代码
transactionTemplate.executeWithoutResult(status -> {
    // 1. 更新 approval → REJECTED
    // 2. 更新 document.status → REJECTED
});
// 事务外：异步删除 MinIO 文件
try {
    minioFileStorageService.delete(storageKey);
} catch (Exception e) {
    log.error("Failed to delete rejected file: {}", storageKey, e);
    // 不抛异常，DB 已正确标记
}
```

## 七、PRD 完整性

### P1-13：缺少文档状态机定义

**问题描述：** PRD 引入了新的文档状态（PENDING_APPROVAL），但未定义完整的状态转换规则。关键问题：

### P1-14：缺失并发场景处理策略

**问题描述：** PRD 未定义以下并发场景的处理方式：

1. 两个管理员同时批准同一文档
2. 一个管理员审批期间，CREATOR 移除了该管理员
3. 用户上传期间，团队被解散

**违反规范：**
- `cross-layer-thinking-guide.md`：Checklist → "Tested with edge cases"

**建议修复：** 使用乐观锁（`version` 字段）或数据库行锁处理审批并发：

```sql
UPDATE team_upload_approval 
SET status = 'APPROVED', reviewer_id = ?, reviewed_at = NOW(), version = version + 1
WHERE id = ? AND status = 'PENDING' AND version = ?
-- 检查 affected rows = 1，否则抛 APPROVAL_ALREADY_PROCESSED
```
